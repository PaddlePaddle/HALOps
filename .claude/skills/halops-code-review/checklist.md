# Review 维度清单

本清单只规定**审查哪些方面**以及**怎样从仓库里找到对应的约定**，不写具体的文件、目录、算子、常量或规则编号。每个维度的具体要求，以 SKILL.md "规范来源"中找到的仓库文件和对照基线为准。所有检查都只针对本次改动。

## A. 正确性与健壮性（P0）

### 对外入口

先在对照基线里看同类入口是怎么写的：开头做了哪些固定动作，比如设备/stream 选择、参数检查。然后对新入口逐项核对：

- **设备与 stream 上下文**：基线入口里有的设备 guard 或 stream 选择，新入口不能少。入口里查询当前设备属性的（SM 数、`cudaGetDevice`、函数属性设置）尤其要看。
- **内存布局假设**：
  - 用 `size()` 代替 `stride()` 的地方，tensor 必须是连续的，或者有检查保证连续。
  - 按向量宽度读写时，要满足对齐要求。
- **dtype**：裸指针强转（如 `reinterpret_cast(data_ptr())`）没有 dtype 保护，关键输入要检查。
- **buffer 容量**：写入 workspace 或输出 buffer 之前，要校验大小。
- **除零与空输入**：除法和取模要放在参数检查之后。0 长度、0 token 输入的处理方式，要和基线一致。
- **常量和运行时 shape 的一致性**：编译期常量与运行时 shape 之间要有校验。不一致时会静默算错的，归为 P0。
- **dispatch 的 default 分支**：switch/dispatch 不能有隐式 default，走到预期之外的分支要报错。
- **检查的数量**：遵守仓库和用户对检查数量的偏好。只建议补那些会导致越界、算错、hang 的检查，不建议加一套完整的防御检查。

### 设备代码与并发

- **跨 kernel 依赖**：dependent kernel（如 PDL）读取前序 kernel 写入的数据，必须在等待原语之后。还要看上游 kernel 在哪里 trigger。
- **内存 proxy 与可见性**：generic store 写、async proxy（TMA 等）读的数据，中间要有 proxy fence。用仓库里同类模式的写法作对照。
- **barrier 的字节数和计数**：要与实际装载的 shape 对应，不能借用一个恰好数值相等的其他常量。
- **类型转换与比较**：有符号转无符号时，负数会变成超大值；int 和 unsigned 混用比较要注意。
- **数值编码**：特殊编码值（NaN、Inf）不能被当作普通值使用。取整方式要与语义一致。
- **inline asm**：涉及内存序的 asm 要声明 memory clobber。

### 通用逻辑

- 边界条件，off-by-one。
- 未初始化的变量。
- 错误被吞掉。
- 资源没有释放。
- 并发竞争。

## B. 规范文档中的编码规则（P1）

逐条读取本目录 `code_standards.md` 和仓库规范文档里的规则，对改动行逐条检查。报问题时注明规则出处（文档名加条目编号或标题）。规范文档里没有写，但下列方面明显影响可维护性的，按通用工程标准报出，规则出处写"通用"，最高定为 P1：

- **注释**：只在关键位置写。不能出现调试过程、废弃思路、迭代或性能实验记录。注释内容要和代码一致。
- **常数**：不能出现来源不明的魔数。来自硬件规则或 tensor 维度的常量，要具名并从源头推导。调参阈值要说明来源。
- **重复与别名**：不要有纯别名，不要重复定义或重复声明。新增的 helper，要先用 grep 确认仓库里没有等价实现。只建议合并逐行确认 100% 相同、合并后不会造成逻辑耦合的代码。
- **死代码与 include**：删掉未使用的函数、字段、形参、模板参数，恒定不变的泛化，以及冗余的 include 和 import。
  - 有的头文件不是自包含的；formatter 也可能重排 include，比如 clang-format 的 IncludeBlocks。所以应该删掉冗余，而不是靠调整顺序来解决问题。
- **函数结构**：函数过长（经验值约 80 行以上）、嵌套过深、内联 lambda 过多，或者有难懂的位运算或索引技巧时，建议拆分、具名，或加一行注释。
- **大 kernel**：global 函数里保留主流程，细节封装成函数。
- **helper 的位置**：按功能集中放置。放在哪里，参照仓库里同类 helper 所在的位置。
- **文件后缀与头文件**：遵守仓库约定的后缀，也就是规范文档的要求加上已有文件的一致做法。device 头文件里不混入 host 专用代码。

## C. 仓库约定（P1/P2）

这些约定通常不写在文档里，需要从对照基线和全仓统计中归纳。归纳方法是：grep 同类文件，看多数文件怎么写。只有绝大多数文件都一致的写法才算约定。

- **文件头**：license 头是否和其他文件一致，写法（注释还是 docstring）是否一致。
- **文档放在哪一层**：接口文档写在哪一层，比如只写在 Python 封装里，或者也写在 C++ 里，要和其他接口一致。
- **语言与命名**：注释语言；大小写和前缀风格；命名空间层级；项目名的写法。头文件里不能在命名空间作用域写 `using namespace`。
- **include/import 的路径风格**：用相对路径还是从根目录开始的路径，要和多数文件一致。
- **跨层一致**：各层的参数顺序、默认值、语义一致；参数传递方式（例如 const 引用）和基线一致。
- **新增公开 API**：按规范文档的要求逐项核对，常见的有：类型标注、docstring（每个参数写明 shape、dtype、作用）、导出列表、文档或 README 里的接口表。如果有多语言文档，要全部同步。
- **构建与产物**：新增的源文件要注册到构建脚本。生成物、日志、二进制、profiling 文件不能进入改动。
- **改名或删除后的残留**：对旧名字做全仓 grep，结果应为 0。docstring、注释、测试 id 里不能再引用已经不存在的文件或函数。
- **文档与变更记录**：改了公开行为，要同步用户文档和 CHANGELOG（如果仓库有）。双语文档两边都要同步。

## D. 单测（P2；正确性覆盖缺口为 P1）

先读规范文档里的测试约定、测试目录的公共配置（如 `conftest.py`、fixture、`tests/utils` 一类的目录）和同类测试文件，再核对：

- **文件与组织**：命名和放置位置是否与同类测试一致。共享的 reference 实现和输入构造是否放在公共目录。只有完全相同的部分才抽成公共代码。
- **风格**：测试框架、参数化方式、数值比较函数、容差常量写法、异常断言方式，都要和同类测试一致。
- **公共配置不能重复设置**：公共配置已经处理的（随机种子、默认设备、硬件不满足时跳过），测试文件里不要再设一遍。
- **禁止项**：不要用 print 调试，不要写绝对路径，不要用环境变量做调试开关，不要在 import 时分配设备资源（以仓库约定为准）。
- **覆盖**：
  - 常规 shape、边界 shape、非法输入、所有支持的精度或模式；
  - 每个 dispatch 分支或档位至少有一个用例能走到；
  - 可选参数为 None 的路径；
  - 新增的每个报错检查，都有对应的异常用例，并且 `match` 和报错文案一致。
- **回归测试**：修 bug 时，要有一个在修复前能复现问题的用例。
- **标记**：仓库如果有快速子集之类的标记约定，新的耗时测试要遵守。

## E. 提交（只在阶段二用户要求提交时检查）

- 提交标题格式按规范文档里的要求。
- 一个提交只解决一个问题，不混入无关的重构或格式化。
